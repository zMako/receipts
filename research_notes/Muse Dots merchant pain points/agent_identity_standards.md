## Key Question 1: Agent identity on the web (Web Bot Auth, Cloudflare, Akamai/DataDome/HUMAN, robots.txt, user-agent strings) and what actually ships

### Takeaway
Web Bot Auth (RFC 9421 HTTP Message Signatures + a `Signature-Agent` header pointing to a JWKS directory at `/.well-known/http-message-signatures-directory`) is the de-facto production mechanism: it is an active IETF WG draft since 1 Sep 2026 and is enforced by Cloudflare, DataDome, Visa TAP and Mastercard, and used experimentally by Google. However, the biggest new consumer agents (Meta Muse, and by extension OpenAI Dots) do not sign and do not even declare an `Agent/` user-agent, so merchants still rely on behavioral bot detection for most agent traffic.

### Cited Findings

**IETF Web Bot Auth**
- On 1 Sep 2026 the protocol became `draft-ietf-webbotauth-httpsig-protocol-00`, an active Web Bot Auth (webbotauth) working-group Internet-Draft, authored by Thibault Meunier (Cloudflare) and Sandor Major (Google); it describes "a protocol for identifying automated traffic using HTTP Message Signatures" with "the Signature-Agent header for key discovery, a JWKS-based key directory format, and a well-known URI for directory access." Related WG drafts: `draft-meunier-webbotauth-registry-03` (Registry and Signature Agent card), `draft-nottingham-webbotauth-use-cases-02`, and `draft-ietf-oauth-client-id-metadata-document-02` (normative reference for the CIMD discovery type) — [IETF datatracker](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/)
- The predecessor `draft-meunier-web-bot-auth-architecture-05` (published 2 Mar 2026, now "Replaced") specifies the headers verbatim: `Signature`, `Signature-Input`, `Signature-Agent` (structured dictionary); required signature components: `@authority` or `@target-uri`, `created`, `expires`, `keyid` (base64url JWK SHA-256 thumbprint per RFC 7638), `tag="web-bot-auth"`; optional `nonce` (base64url-encoded 64 bytes). Key directory well-known URL: `/.well-known/http-message-signatures-directory`. Algorithms: EdDSA on edwards25519 and RSASSA-PSS with SHA-512. Verifier must validate per RFC 9421 §3.2, confirm `tag="web-bot-auth"`, check `keyid` is known or fetch from the `Signature-Agent` directory, validate `expires`, and optionally enforce nonce uniqueness ("Clients are the one controlling the nonce ... it is the origin's responsibility to enforce it") — [draft-meunier-web-bot-auth-architecture](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture)
- Example directory format from the draft: `{"keys":[{"kty":"OKP","crv":"Ed25519","kid":"...","x":"...","use":"sig","nbf":...,"exp":...}]}` — [draft-meunier-web-bot-auth-architecture](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture)
- A secondary source notes the IETF WG's April 2026 milestones "passed without a published standards-track document" before the September adoption — [nohacks.co](https://nohacks.co/blog/ai-user-agents-landscape-2026)

**Cloudflare Verified Bots and signed agents (production)**
- Cloudflare designates bots "Verified" when they "declare who [they are] deterministically" via cryptographic signatures, published IPs, or reverse DNS and "obey robots.txt and crawl directives". Two validation methods: Web Bot Auth (cryptographic signatures) and IP validation (published IP lists plus stable user-agent strings). "As of July 1, 2026, signed agents now receive Verified classification, tracked through a new 'Direct versus Intermediary access' metadata field in BotBase." Behavior categories: Search, Agent, Training, Transact, Data Collection, Security Testing, SEO, Ads Verification, Social/Link Preview, Feed Fetching, Monitoring & Operations. Operational model: Direct (single operator on own infra) vs Intermediary (agentic services operated by many end users). Bot operators apply via the dashboard; approved bots appear in BotBase and Cloudflare Radar — [Cloudflare Verified bots docs](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)
- The signed-agents doc states the new classifications "are not individual fields in WAF custom rules, but have backwards-compatible categories from the original taxonomy"; examples under the legacy "AI Assistant" category include Perplexity-User and DuckAssistBot — [Cloudflare signed agents docs](https://developers.cloudflare.com/bots/concepts/bot/signed-agents/)
- Cloudflare's agentic-commerce integration (published 24 Oct 2025, updated 15 Jul 2026) performs seven validation checks: (1) signature headers present, (2) retrieve public key from directory, (3) validate `created`/`expires`, (4) check nonce uniqueness, (5) verify tag validity, (6) reconstruct signature base, (7) Ed25519 verification. Example header: `Signature-Input: sig2=("@authority" "@path"); created=1735689600; expires=1735693200; keyid="..."; alg="Ed25519"; nonce="..."; tag="web-bot-auth"` / `Signature: sig2=:...:`. Payment-network tags: `tag="agent-browser-auth"` (browsing) and `tag="agent-payer-auth"` (payment). "Managed rulesets planned" and "Cloudflare Agent SDK supports these protocols (coming in following months)"; American Express also builds on Web Bot Auth — [Cloudflare blog](https://blog.cloudflare.com/secure-agentic-commerce/)
- A secondary blog claims a 2 Jun 2026 Cloudflare Bot Management update launched with 19 verified AI agents (ChatGPT Atlas, Claude in Chrome, Perplexity Browser, Gemini Agent Mode, Brave Leo, Arc Browse for Me, ...) covering "an estimated 84% of identified AI browser traffic"; the same source calls Web Bot Auth a "W3C ... specification finalized in May 2026", which is inconsistent with the IETF venue and should be treated as unreliable — [pravinkumar.co](https://www.pravinkumar.co/blog/cloudflare-june-2026-bot-management-webflow-protection-2026)

### Inferences
- A merchant's practical detection stack in Oct 2026 is three-tiered: (1) verify RFC 9421 signatures with `tag="web-bot-auth"` (or Visa/Mastercard tags) against the `Signature-Agent` JWKS directory; (2) fall back to UA-token + published-IP-list validation for crawler-style agents (OpenAI, Google, Anthropic, Perplexity); (3) treat everything else, including Muse/Dots cloud-browser traffic, as unverified human-like traffic subject to behavioral detection.
- Because Google's user-triggered fetchers ignore robots.txt, robots.txt is a declaration channel for crawlers rather than an enforcement tool for shopping agents.
- The `Agent/[name]` UA convention Amazon mandates is a contractual, not cryptographic, control; any merchant adopting it should pair it with Web Bot Auth for the agents that do sign.

### Gaps
- No primary documentation found for Muse's or Dots' actual HTTP fingerprint (UA string, headers); DataDome's threat-research piece is the likely primary source but returned 403.
- No evidence found that OpenAI Atlas/ChatGPT agent, Claude in Chrome or Perplexity Comet publish a `Signature-Agent` directory URL; the "19 verified agents" claim is from one unverified secondary blog.
- No sources found on an "ai.txt" convention in 2026; it does not appear in any vendor documentation retrieved.
- Cloudflare's exact WAF rule field names for signed agents (e.g. whether `cf.bot_management.verified_bot` or `cf.verified_bot_category` carry the Direct/Intermediary flag) were not stated in the retrieved docs.

## Key Question 2: Agent payments (Visa TAP/Intelligent Commerce, Mastercard Agent Pay, Stripe ACP/SPT, Google AP2, PayPal, Shopify) and how a merchant receives proof a human authorized a purchase

### Takeaway
Four partly overlapping primitives give merchants proof of authorization: Visa TAP's signed "Agentic Consumer Recognition" object carrying an OIDC-style `idToken` plus a Visa Payment Passkey; Mastercard Agentic Tokens bound to agent, merchant scope and consent; AP2's user-signed Cart/Payment Mandates (W3C Verifiable Credentials) carried inside UCP; and Stripe SPTs which prove only an allowance (amount/expiry/merchant) rather than human presence. Only TAP, Agent Pay and SPT have documented live transactions; ChatGPT's in-chat Instant Checkout was wound down in March 2026.

### Cited Findings

**Visa Trusted Agent Protocol (TAP) and Intelligent Commerce**
- Visa announced TAP (Oct 2025) as "a standardized, cryptographic method for an AI agent to prove its identity and associated authorization directly to merchants"; launch partners on the merchant/processor side: Adyen, Ant International, Checkout.com, Coinbase, CyberSource, Elavon, Fiserv, Microsoft, Nuvei, Shopify, Stripe, Worldpay; Visa cites "AI traffic to U.S. retail up 4,700%" (search summaries) — [Visa newsroom](https://corporate.visa.com/en/sites/visa-perspectives/newsroom/visa-unveils-trusted-agent-protocol-for-ai-commerce.html), [Visa IR](https://investor.visa.com/news/news-details/2025/Visa-Introduces-Trusted-Agent-Protocol-An-Ecosystem-Led-Framework-for-AI-Commerce/default.aspx)
- Spec (verbatim): headers `Signature-Input` and `Signature`; tags `"agent-browser-auth"` (product detail pages, inventory checks) and `"agent-payer-auth"` (checkout). Agent Recognition Signature components: `@authority`, `@path`, `created`, `keyid`, `expires`, `tag`, `alg`, `nonce`. **Agentic Consumer Recognition** object: `nonce`, `idToken`, `contextualData`, `kid`, `alg`, `signature`; `contextualData` fields `countryCode`, `zip`, `ipAddress`, `deviceData`. **Agentic Payment Container**: `nonce`, `paymentCredentialsHash`, `kid`, `alg`, `signature`; card metadata `lastFour`, `paymentAccountReference`, `shortDescription`, `CardData`. `idToken` JWT claims: `iss`, `sub`, `aud`, `exp`, `iat`, `jti`, `auth_time`, `amr`, `phone_number`, `phone_number_verified`, `email`, `email_verified`, `phone_number_mask`, `email_mask`. Visa publishes keys at `https://mcp.visa.com/.well-known/jwks`. Merchant verification: check tag, minimum fields, timestamps within an 8-minute window (created in past, expires in future), nonce replay check, fetch key by `keyid`, construct signature base, verify. Python sample provided for signature-base construction. No version/date/availability tier stated — [Visa TAP spec](https://developer.visa.com/capabilities/trusted-agent-protocol/trusted-agent-protocol-specifications)
- Visa's GitHub sample: Python `agent-registry` (port 8001, "agent public keys and metadata"), `tap-agent`, `merchant-backend`; Node.js `cdn-proxy`; React `merchant-frontend`; merchants verify the signature is "current", "bound to your domain and the specific operation", preventing "relays or replays" — [visa/trusted-agent-protocol](https://github.com/visa/trusted-agent-protocol)
- Live activity (secondary sources): Nuvei completed a live PoC with Visa, Arvato Systems and Kings and Priests on 2 Jul 2026 with multiple European issuers settling on live Visa rails — [Nuvei](https://www.nuvei.com/posts/nuvei-supports-visa-trusted-agent-protocol-to-advance-agentic-commerce); on 24 Sep 2026 Cleverbridge completed France's first passkey-authenticated agentic payment (Visa test agent, TAP verification, Visa Payment Passkey, Revolut-issued card); ~30 European issuers transacting by Jul 2026 (merchants lastminute.com, Frasers); Intelligent Commerce Connect live via Visa Acceptance Platform since 8 Apr 2026 — [ScriptMasterLabs](https://scriptmasterlabs.com/visa-trusted-agent-protocol) (cites Business Wire; not independently verified)

Note: OpenAI's hosted checkout spec page still shows `API-Version: 2025-09-12`.
- ACP Agentic Checkout spec (merchant-hosted REST API called by the agent platform): required headers `Authorization: Bearer <api_key>`, `API-Version`, `Idempotency-Key`, `Request-Id`, `Signature` ("Base64 encoded signature of the request body"), `Timestamp` (RFC 3339), `User-Agent`, `Accept-Language`. Webhooks `order_created`/`order_updated` with `status` in created, manual_review, confirmed, canceled, shipped, fulfilled, delivered via HMAC header "`Merchant_Name-Signature`" using a key provided by OpenAI. "The spec does not specify risk/fraud signal fields" — [OpenAI Agentic Checkout spec](https://developers.openai.com/commerce/specs/checkout)
- Instant Checkout launched 29 Sep 2025 (Etsy first, then Shopify merchants, Stripe-powered); on 24 Mar 2026 OpenAI "confirmed ... it's moving away from processing purchases directly inside ChatGPT", pivoting to discovery with merchants handling checkout in their own apps (some inside ChatGPT); "only around 30 Shopify merchants were available through Instant Checkout as of early March"; ACP was expanded for product feeds/promotions; Target, Sephora, Nordstrom, Lowe's, Best Buy, Home Depot, Wayfair integrated for discovery (search summaries) — [CNBC](https://www.cnbc.com/2026/03/24/openai-revamps-shopping-experience-in-chatgpt-after-instant-checkout.html), [Enterprise DNA](https://enterprisedna.co/resources/news/openai-agentic-commerce-protocol-walmart-sparky/), [presenc.ai](https://presenc.ai/research/chatgpt-instant-checkout-shutdown-analysis-2026)

**Google AP2**
- Announced 16 Sep 2025 with 60+ partners (Adyen, Amex, Mastercard, PayPal, Revolut, Worldpay, Etsy, Salesforce, Shopee, Forter, Okta, 1Password, ...). Three mandates: Intent Mandate (user's request), Cart Mandate ("secure, unchangeable record of exact items and price" signed by the user before purchase), Payment Mandate (links payment method to cart). "All mandates are signed by verifiable credentials (VCs)". Human-present: user signs the Cart Mandate in real time; human-not-present: user signs a detailed Intent Mandate up front and the agent generates the Cart Mandate when conditions are met. The chain yields "a non-repudiable audit trail" answering authorization, authenticity and accountability. AP2 is an extension of A2A and MCP; an A2A x402 extension covers stablecoin payments — [Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)
- GitHub repo: Python SDK (`code/sdk/python/ap2/`), Go and Android samples, Apache-2.0, roles shopping agent / merchant endpoint / credentials provider / payment processor — [google-agentic-commerce/AP2](https://github.com/google-agentic-commerce/AP2)
- Secondary: AP2 v0.2.0 shipped April 2026 and AP2 was "contributed to the FIDO Alliance in April 2026"; mandates are W3C Verifiable Credentials "signed by the user's wallet or the agent's key" — [eco.com](https://eco.com/support/en/articles/15192002-ap2-protocol-explained-google-s-agentic-commerce-standard-2026)

**UCP / Shopify**
- UCP profiles declare `payment_handlers`; payment instruments carry `handler_id`; UCP supports "payment mandates and verifiable credentials" (AP2) for "cryptographic proof of user consent"; checkout states `incomplete`, `requires_escalation` (hand-off via `continue_url`), `ready_for_complete` — [ucp.dev](https://ucp.dev/), [Shopify Engineering](https://shopify.engineering/ucp)
- 28 Sep 2026: Shopify launched WebMCP support for checkout "including Shop Pay, for all eligible Shopify merchants"; tools `get_checkout`, `update_checkout`, `complete_checkout`; agents may submit "with the buyer's authorization"; partners Muse and Instinct; "no mention of agent identification or verification mechanisms" in the announcement — [TechCrunch](https://techcrunch.com/2026/09/28/shopify-opens-checkout-to-browser-based-ai-agents/)
- Shopify's Checkout MCP: "trusted agents can complete purchases directly"; trust tiers derive from the agent's UCP profile — [shopify.dev/docs/agents](https://shopify.dev/docs/agents)

**PayPal**
- PayPal's Agent Toolkit exposes payments, invoicing, dispute handling, shipment tracking, catalog, subscription and reporting APIs to OpenAI Agent SDK, LangChain, Bedrock, CrewAI, Vercel AI SDK and MCP — [PayPal developer blog](https://developer.paypal.com/community/blog/paypal-agentic-ai-toolkit/); "Agent Ready" (accept agent-originated payments with no code change) and "Store Sync" (catalog to AI discovery platforms) announced 28 Oct 2025, Agent Ready rolling out early 2026 — [Digital Commerce 360](https://www.digitalcommerce360.com/2025/10/28/paypal-agentic-commerce-ai-driven-shopping-services/), [PR Newswire](https://www.prnewswire.com/news-releases/paypal-launches-agentic-commerce-services-to-power-ai-driven-shopping-302596548.html)

### Inferences
- "Proof a human authorized" differs by rail: TAP gives a signed consumer `idToken` with `amr`/`auth_time` claims (so a merchant can see passkey/MFA method and time); AP2 gives a user-signed Cart Mandate hash chain; Mastercard pushes the proof into the token/network layer (merchant sees an agentic indicator and risk score rather than a signature); Stripe SPT gives no human-presence proof, only a bounded allowance the agent platform vouches for.
- For a hackathon, Stripe SPT is the only one with a self-serve sandbox (`test_helpers` + `link-cli`); TAP and AP2 have runnable reference repos but no self-serve network credentials.

## Key Question 3: Agent-readable commerce (Shopify catalog for agents, OpenAI product feeds, Google Merchant Center, llms.txt/agents.md, merchant MCP servers, schema.org)

### Takeaway
Feeds remain the backbone: OpenAI's product feed spec (9 required fields, `is_eligible_checkout` flag), Google Merchant Center as the UCP entry point, and Shopify's Catalog/agentic storefronts which are on by default. Shopify additionally exposes Global/Storefront Catalog, Cart, Checkout and Order MCP servers and (per secondary sources) auto-generates `/llms.txt`, `/llms-full.txt` and `/agents.md`; no schema.org agent extension was found.

### Cited Findings
- OpenAI product feed required fields: `item_id`, `title` (≤150 chars), `description` (≤5,000), `url` (public HTTPS), `brand`, `seller_name`, `image_url`, `availability` (`in_stock`, `out_of_stock`, `pre_order`, `backorder`, `unknown`), `price` (e.g. `79.99 USD`); optional `is_eligible_search` (default true), `is_eligible_checkout` ("requires separate integration enablement"), `is_ads_eligible`; formats JSONL, gzipped CSV/TSV, Google-compatible delimited files; delivery per the file-upload guide at https://developers.openai.com/commerce/specs/file-upload/overview — [OpenAI feed spec](https://developers.openai.com/commerce/specs/feed)
- Secondary: feed must be refreshed "as often as every 15 minutes"; Parquet (zstd) preferred — [Lengow](https://www.lengow.com/get-to-know-more/chatgpt-product-feed)
- Shopify Agentic storefronts are "active by default for eligible stores"; channels listed: ChatGPT, Google AI Mode and Gemini, Microsoft Copilot, Meta (Muse); managed under Sales channels > Agentic; orders show "with channel or referrer attribution"; products flow via Shopify Catalog or the Google & YouTube channel; merchants must accept the Agentic Storefronts Supplemental Terms — [Shopify Help Center](https://help.shopify.com/en/manual/online-sales-channels/agentic-storefronts)
- Shopify developer surface for agents: UCP, Shopify AI Toolkit (UCP-compliant MCP servers), UCP CLI, Global Catalog ("hundreds of millions of Shopify product listings"), Storefront Catalog, Cart MCP, Checkout MCP, Order MCP (`get_order`), Order Webhooks (fulfillment, refunds, returns, exchanges, cancellations); agents "Define a profile so Shopify can verify your agent and apply the right rate limits and tool access"; Universal Cart API in early access via waitlist — [shopify.dev/docs/agents](https://shopify.dev/docs/agents)
- Secondary: in May 2026 Shopify enabled `/llms.txt`, `/llms-full.txt` and `/agents.md` on all stores, with `/agents.md` as "the canonical agent discovery URL"; "Shopify stores are UCP-enabled by default" — [Craftshift](https://craftshift.com/shopify-native-llms-txt-agentic-discovery-rollout/), [htt.it](https://www.htt.it/en/shopify-llms-txt-agents-md-agentic-commerce-guide/)
- Google announced UCP on 11 Jan 2026 at NRF with Shopify, Etsy, Wayfair, Target and Walmart, "with Merchant Center as the entry point"; Merchant Center data surfaces in AI Mode, virtual try-on and agentic checkout — [Shopify blog](https://www.shopify.com/blog/google-ai-shopping), [Digital Commerce 360](https://www.digitalcommerce360.com/2026/01/12/shopify-universal-commerce-protocol-open-standard-agentic-ai/)

### Inferences
- A merchant that publishes one Google-compatible feed plus a `/.well-known/ucp` profile covers ChatGPT discovery, Google AI Mode/Gemini, Copilot and Shopify-channel agents; checkout eligibility is a separate enablement per platform.

## Key Question 4: Post-purchase agent-to-merchant communication (returns, disputes, support) and standards for an agent to prove it represents a specific customer

### Takeaway
Post-purchase is handled through UCP's Orders capability (signed webhooks, return policy extension), Shopify's Order MCP/webhooks, ACP's `order_updated` webhooks and PayPal's toolkit (disputes, tracking). The only standardized customer-delegation mechanism found is OAuth 2.0 identity linking in UCP (`dev.ucp.common.identity_linking`), plus Visa TAP's consumer `idToken`; there is no widely adopted verifiable-credential standard for "this agent represents customer X" in support channels.

### Cited Findings
- UCP Orders: capability `dev.ucp.shopping.order` "enables order retrieval and webhooks"; "Business-to-platform webhooks transmitting order events or returns must be cryptographically signed"; verifiers use the profile's `keys[]`; return policy capability `dev.ucp.shopping.policy.return` — [ucp.dev overview](https://ucp.dev/specification/overview), [ucp.dev](https://ucp.dev/)
- UCP Identity Linking "uses OAuth 2.0 standard"; the capability `dev.ucp.common.identity_linking` carries a `config` object with `providers` and `scopes`; merchants expose `/.well-known/oauth-authorization-server` with `scopes_supported`, `authorization_endpoint`, `token_endpoint`, `revocation_endpoint` — [ucp.dev overview](https://ucp.dev/specification/overview), [ucp.dev](https://ucp.dev/)
- Platforms advertise themselves with `UCP-Agent: profile="https://agent.example/profiles/shopping-agent.json"` and merchants "verify the agent's identity through HTTP Message Signatures or other authentication mechanisms"; a profile carrying `keys[]` "serves as a valid JWK Set — reusable as a Web Bot Auth key source when the `Signature-Agent` header selects it" — [ucp.dev overview](https://ucp.dev/specification/overview)
- Shopify Order MCP exposes `get_order`; Order Webhooks cover "fulfillment events, refunds, returns, exchanges, and cancellations" — [shopify.dev/docs/agents](https://shopify.dev/docs/agents)
- ACP merchants emit `order_created`/`order_updated` webhooks (statuses incl. `manual_review`, `canceled`, `shipped`, `fulfilled`) signed with HMAC — [OpenAI checkout spec](https://developers.openai.com/commerce/specs/checkout)
- PayPal Agent Toolkit covers "dispute handling, shipment tracking" and exposes these over MCP — [PayPal developer blog](https://developer.paypal.com/community/blog/paypal-agentic-ai-toolkit/)
- Visa TAP's `idToken` (OIDC claims `sub`, `amr`, `auth_time`, masked `email`/`phone_number`) is the "linked and signed consumer/device identity ... provided in the message request body" (search summary) — [Visa TAP spec](https://developer.visa.com/capabilities/trusted-agent-protocol/trusted-agent-protocol-specifications), [eco.com](https://eco.com/support/en/articles/14845482-visa-trusted-agent-protocol-tap-explained)
- Akamai KYA aims to verify an agent "is also verified as acting on behalf of a specific, authorized individual" — [Akamai PR](https://www.akamai.com/newsroom/press-release/akamai-unveils-agentic-security-framework-to-power-trusted-ai-driven-interactions-and-commerce)
- Muse "shops, negotiates and handles refunds for consumers" (search summary) — [CBS News](https://www.cbsnews.com/news/meta-ai-agent-muse-shopping/)
- Web Bot Auth's registry draft adds a "Signature Agent card" and the protocol references OAuth Client ID Metadata Documents for discovery — [IETF datatracker](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/)

### Inferences
- The realistic path for "agent acting for customer X" in support/returns is: agent authenticates itself via Web Bot Auth/UCP-Agent, the customer links their merchant account to the agent platform via OAuth (UCP identity linking), and the merchant authorizes on the OAuth token's scopes. Verifiable credentials appear only inside AP2 mandates, not in support flows.
- Email-based agent support (Muse "negotiates ... handles refunds") has no identity standard at all; merchants will see those as ordinary customer emails.

### Gaps
- No standard found for agent-initiated disputes/chargebacks; Mastercard/Visa liability rules for agentic transactions were not located in retrievable primary docs.
- The UCP identity-linking scope names and the exact Orders webhook payloads were not retrieved (overview page only).

## Key Question 6: Known weaknesses (spoofing, unsigned agents, mixed human/agent sessions, impersonation)

### Takeaway
Signatures prove key possession, not operator intent or human authorization; they only enable allow-listing, since bad actors can mint or rotate keys. The dominant 2026 failure mode is not spoofing but silence: Muse-style cloud browsers present as plain Chromium, and agentic browsers blend human and automated control in one session with the user's own cookies.

### Cited Findings
- Hacker News: "key generation is free, so being a well-behaved unknown bot is the same as being an unidentified bot ... It is only useful for whitelisting bots, not for banning bad ones" and "bad ones can rotate keys" (user sneak); centralization objections ("Register with CF is the specific part I object to", palmfacehn); defense: "Nothing about this is limited to Cloudflare" (bobbiechen) — [HN thread](https://news.ycombinator.com/item?id=45055452)
- Prosopo (1 Sep 2026): "A signature tells you who. It does not tell you what for"; a verified agent "can still request your entire product catalogue at a rate nobody agreed to"; treat signatures as "a strong signal rather than a free pass" and keep behavioral scoring for all traffic — [Prosopo](https://prosopo.io/blog/web-bot-auth-signed-agents/)
- Castle (Aug 2025): Comet "might start with human interaction and shift into automated mode mid-flow, using the same browser and fingerprint"; Skyvern uses "high-quality US residential and ISP proxies, including IPs associated with AT&T"; Browserbase/Skyvern "strip out automation markers, rotate through residential IPs, and avoid exposing any identifying headers"; even signed Operator traffic is ambiguous ("brute-force logins") — [Castle blog](https://blog.castle.io/from-detection-to-trust-the-evolving-challenge-of-ai-bot-authentication/)
- A signature "says nothing about who operates the Agent, whether the Agent is benign, or whether the request is authorized" (search summary of community analysis) — [rohitghumare.com](https://rohitghumare.com/blog/muse-at-the-storefront/)
- Muse traffic was "indistinguishable from a person"; Amazon's UA-based robots.txt "only worked if agents voluntarily declared themselves" — [jahanzaib.ai](https://www.jahanzaib.ai/blog/amazon-blocks-meta-muse-ai-agent-identity)
- Muse stores user credentials in per-user VMs; Meta claims Muse "has no visibility into people's passwords or payment methods" — [jahanzaib.ai](https://www.jahanzaib.ai/blog/amazon-blocks-meta-muse-ai-agent-identity); Security Boulevard on Muse's per-user computer — [Security Boulevard](https://securityboulevard.com/2026/10/metas-muse-agent-will-help-you-root-around-the-computer-it-gives-every-user/)
- Claimed implementation gaps: "Cloudflare's verifier does not validate nonces and does not guard against replay attacks using a nonce database, and the core drafts themselves were renamed and restructured multiple times in 2026" (search summary) — [SEOJuice](https://seojuice.com/blog/web-bot-auth-googlebot-verification-2026); contradicted by Cloudflare's own description of a nonce-uniqueness check in its seven validation steps — [Cloudflare blog](https://blog.cloudflare.com/secure-agentic-commerce/)
- Google's user-triggered fetchers "generally ignore robots.txt rules" — [Google docs](https://developers.google.com/search/docs/crawling-indexing/google-user-triggered-fetchers)
- Mastercard's 30 Sep 2026 countermeasure: a "probability score indicating likelihood a transaction was initiated by an AI agent" for issuers and merchants — [PYMNTS](https://www.pymnts.com/mastercard/2026/mastercard-deploys-new-risk-insights-to-support-agentic-payments/)
- Research: an arXiv paper surveys AI-agent identity "standards, gaps, and research directions" and another proposes "aCAPTCHA" for agent admission — [arXiv 2604.23280](https://arxiv.org/pdf/2604.23280), [arXiv 2603.07116](https://arxiv.org/pdf/2603.07116)

### Inferences
- Merchants should model three populations separately: signed agents (policy by identity + rate limits), declared-but-unsigned agents (UA token + IP list), and undeclared agents in real browsers (behavioral detection, step-up authentication at checkout, network-level agentic probability scores).
- Replay protection is origin-side: a merchant verifying signatures itself must keep its own nonce store, since the draft leaves enforcement to the origin.

### Gaps
- No quantitative data found on how often attackers impersonate legitimate agents via stolen or forged signatures; the attack surface is argued, not measured.
- Whether Cloudflare's production verifier enforces nonces is disputed between a secondary blog and Cloudflare's own post; not independently verifiable here.
