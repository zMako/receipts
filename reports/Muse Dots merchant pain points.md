# Unsigned Shopping Agents Push Dispute Risk Onto Merchants

Meta's Muse (launched 8 Sept 2026) and OpenAI's Dots (launched 29 Sept 2026) are cloud-hosted personal agents that shop by driving a real Chromium browser in a per-user virtual machine, and neither identifies itself to the websites it visits, so to a merchant their checkouts look like a fast, history-less human session from data-centre address space. Muse pays with Stripe Link single-use cards or Shop Pay, Dots uses cards already saved at the merchant after a per-transaction approval click, and in both cases the merchant stays merchant of record, which means every wrong-variant order, "I didn't mean to buy that" return, and "my agent did it" chargeback lands on the merchant's P&L rather than Meta's or OpenAI's. The loudest first-person complaints today are not yet about Muse or Dots orders (checkout has been live for under two weeks) but about adjacent, measurable harms: Amazon sellers losing A-to-Z claims because Rufus told shoppers an item fits, Shopify merchants watching pixels, consent and upsell apps fail on "ghost" in-chat orders, fraud tooling that cannot tell a customer's agent from a card-tester (**only 23% of merchants can identify agent traffic and the purchases it produces**), and forced default enrolment with no clean opt-out. Underneath those complaints sit three structural problems a hackathon team can attack: returns abuse that already runs at **9–15% of all returns (~$100B/yr)** and that wallet-backed agents make effortless; chargeback rules (Visa CE 3.0, VAMP at 1.5%) that require IP and device evidence agent orders do not produce; and an identity stack (IETF Web Bot Auth, Visa TAP, Mastercard Agent Pay, Stripe SPT, UCP) that exists on paper but that Muse and Dots do not use. A merchant-side "returns-abuse and dispute screener" that joins order, return, carrier and dispute data per order, classifies traffic into signed, declared and undeclared agent populations, persists a chargeback-grade mandate record at checkout, and routes likely-friendly-fraud cases into pre-dispute refunds rather than representment fills a gap no vendor currently covers for SMB merchants.

## Muse and Dots are cloud Chromium browsers that look like ordinary shoppers

Muse is the clearer of the two architecturally because Meta published its security design. Each user gets a dedicated isolated Linux VM; the agent harness runs in a `systemd-nspawn` container with root mapped to an unprivileged host user, and a separate permission authority called Sentinel evaluates every outbound request at L4/L7 (hostname, IP, port, method, path), inserts real credentials just-in-time via surrogate tokens, and auto-allows "clean, narrowly-bounded requests" ([Meta Research](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)). The browser is "a real up-to-date Chromium based browser running behind a virtualization layer"; the sub-agent sees an accessibility-tree snapshot rather than raw DOM and cannot execute JavaScript in page context ([Meta Research](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)). A black-box test found the VM is Ubuntu 24.04.5 on 2 vCPU AMD EPYC with 7.7 GiB RAM, with a model id of `ipnext/avocado-5.16-v4`, and that burst-spawning 120 sub-agents failed **72.5%** of the time while staggered spawns failed 0% ([blog.cygankiewicz.com](https://blog.cygankiewicz.com/en/meta-muse-black-box-testing/)). Meta's own launch wording is the merchant-relevant part: "If it has no API at all … the agent can use the service through a browser the way you would" ([DEV Community](https://dev.to/axrisi/meta-muse-blocked-by-amazon-the-ai-shopping-agent-fight-explained-3agp)). Zuckerberg's stated business model is transactional: "over time we will profit by taking a small fee from transactions" ([TechCrunch](https://techcrunch.com/2026/09/23/everything-new-coming-to-metas-ai-agent-muse/)), and the app reached #1 on the US App Store by 18 Sept with third-party download estimates ranging from **2.3M to 5.6M** ([Yahoo Finance](https://finance.yahoo.com/technology/ai/articles/1-reason-why-meta-muse-151831317.html)).

What matters for a screener is how Muse presents on the wire. DataDome's threat research found "no custom User-Agent, no declared header that says 'an AI agent is driving this session'"; sessions present as "an entirely unremarkable desktop Chrome browser on Linux," egress through "generic edge infrastructure like Cloudflare or Fastly" with no published IP range or signed requests, and client-side fingerprints across unrelated sites that were "almost total[ly]" identical, "suggesting the same sandboxed image deployment rather than different users" ([DataDome](https://datadome.co/threat-research/meta-muse-doesnt-declare-itself-heres-why-that-matters/)). Meta's safety post is silent on user-agent strings, robots.txt and rate limits ([Meta Research](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)). That uniform fingerprint is the one exploitable Muse signal today, and Meta can randomize it at any time. Payments are bounded: for new merchants Muse uses Stripe Link single-use card numbers "tied to that particular merchant, a particular dollar amount, and only valid for a limited period of time," with human approval "triggered for every checkout on pre-authorized sites" ([Meta Research](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)); Shop Pay went live 24 Sept and PayPal is announced ([Naughton & Bird](https://naughtonandbird.com/signals/shopify-meta-ai-channel-agentic-storefronts)). On Shopify, "Merchant remains the merchant of record; orders attributed to Meta appear in Shopify admin like other channel orders," direct checkout carries no fee beyond normal processing, and the channel is on by default for eligible stores ([Shopify Help Center](https://help.shopify.com/en/manual/online-sales-channels/agentic-storefronts); [Naughton & Bird](https://naughtonandbird.com/signals/shopify-meta-ai-channel-agentic-storefronts)). Meta's help page puts liability squarely on the shopper: "You're responsible for all transactions your Muse makes on your behalf" ([Yahoo Finance](https://finance.yahoo.com/technology/ai/articles/metas-own-fine-print-says-210000032.html)), and no Meta policy on returns, cancellations or chargebacks for Muse purchases exists.

Amazon's response is the defining merchant-side event of the month. On the night of 20/21 Sept Muse users hit an anti-bot wall and the message "Continued access by an unauthorized AI agent violates Amazon's Conditions of Use" ([The Register](https://www.theregister.com/ai-and-ml/2026/09/21/amazon-shows-metas-muse-ai-shopping-agent-the-door/5297777)). Amazon's three stated grounds were that Meta never disclosed Muse would access Amazon, that Muse "does not identify itself," and that it "appears to capture and store customer credentials" ([Campaign](https://www.campaignlive.com/article/amazon-blocks-metas-muse-shopping-its-platform/1970733)). Amazon's Agent Terms require the string `Agent/[agent name]` in the user agent and forbid mimicking human keystrokes or circumventing CAPTCHAs, and Muse includes none of it ([jahanzaib.ai](https://www.jahanzaib.ai/blog/amazon-blocks-meta-muse-ai-agent-identity)). The legal ground is shaky, though: in Amazon v. Perplexity the Ninth Circuit held on 4 Aug 2026 that the user, not the agent company, "accesses" Amazon's computers under the CFAA ([Decrypt](https://decrypt.co/360629/amazon-perplexity-comet-court-order-agentic-commerce)), and Amazon's earlier technical fingerprint for Comet was evaded within 24 hours ([TechTimes](https://www.techtimes.com/articles/327940/20260923/amazon-blocks-meta-muse-using-standards-it-ignores-its-own-shopping-agent.htm)). Meanwhile Walmart, Best Buy, Gap, Sephora, Ulta, Wayfair, DICK'S and others signed on as Muse partners at Connect ([Meta Newsroom](https://about.fb.com/news/2026/09/the-biggest-news-from-connect-2026/)), eBay banned buy-for-me agents in its Feb 2026 user agreement, and Resy told CNN it "does not currently permit unapproved third-party bots or agents" while OpenTable integrated ([GSPANN](https://www.gspann.com/insights/blog/ai-shopping-agents-retailer-terms); [CNN](https://www.cnn.com/2026/09/23/tech/ai-agent-restaurant-reservations-instinct-resy-cec)).

Dots is a persistence-and-autonomy layer over ChatGPT rather than a new commerce product. "Each dot runs on GPT-6 Astra and works from its own cloud computer and browser… works across 4,000+ apps through ChatGPT" ([OpenAI](https://openai.com/index/introducing-dots/)), gated to Pro ($100–$500/mo), Business Premium and Enterprise, excluded for Pro users in the EEA, UK and Switzerland, and desktop-only to set up ([eesel.ai](https://www.eesel.ai/blog/openai-dots); [NBC News](https://www.nbcnews.com/tech/tech-news/openai-launches-dots-ai-agents-safety-questions-rcna600338)). Its control model is three-layered: Custom Rules map actions to autonomous, pre-approved, ask-first or hand-off; an auto-review system checks consequential actions; and some actions are hard-coded, so password changes and fund transfers always return to the user and card purchases "need advance approval specific to that transaction" ([VentureBeat](https://venturebeat.com/technology/openai-launches-dots-always-on-ai-agent-coworkers-and-chatgpt-space-where-they-can-collaborate-with-human-teams); [eesel.ai](https://www.eesel.ai/blog/openai-dots)). Background "proactive research" is read-only ([traictory](https://traictory.com/news/2026-09-30-openai-dots-agents)). The most consequential architectural fact for merchants is that "plugin permissions are shared across dots, ChatGPT, ChatGPT Work, and Codex" ([OpenAI help center](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs)), so a Shopify plugin a merchant granted for one-off chat use (which can "create discount codes" and "manage inventory") becomes available to an always-on agent without a new consent step ([The Keyword](https://www.thekeyword.co/news/openai-dots-marketing)). OpenAI's crawler docs still list only GPTBot, ChatGPT-User, OAI-SearchBot and OAI-AdsBot with published IP JSON files and no dots token ([OpenAI developers](https://developers.openai.com/api/docs/bots)); the only evidence of OpenAI agents signing requests is from Aug 2025, when Operator sent `Signature`, `Signature-Input` and `Signature-Agent: "https://chatgpt.com"` headers with keys at `https://chatgpt.com/.well-known/http-message-signatures-directory` ([Castle](https://blog.castle.io/how-to-authenticate-openai-operator-requests-using-http-message-signatures/)). Whether the Dots cloud browser does the same is unconfirmed, and the older ChatGPT Agent got stuck in infinite Cloudflare "Verify you are human" loops on sites including a Shopify login ([OpenAI Developer Community](https://community.openai.com/t/chatgpt-agent-not-passing-cloudflare-verification-for-chatgpt-com/1336765)). OpenAI's commerce plumbing (ACP feeds, Instant Checkout) is documented for ChatGPT, not Dots, and Instant Checkout was wound down in March 2026 with only ~30 Shopify merchants live ([CNBC](https://www.cnbc.com/2026/03/24/openai-revamps-shopping-experience-in-chatgpt-after-instant-checkout.html)).

Both products therefore concentrate purchase risk in the human approval click. Under the Uniform Electronic Transactions Act an electronic record is attributed to the person whose act it was, so "a dot buying the wrong flight on a saved card after you clicked yes would be attributed to the user who approved it," and attention data cited in the same analysis shows people blocked dangerous commands only 13.6% of the time, with attention falling to ~5% after 50 prompts ([Business Model Analyst](https://businessmodelanalyst.com/openai-dots-approval-click-liability/)). The consumer is liable on paper; the merchant absorbs the return in practice. Muse's documented misbehaviour already shows the shape of this: on Facebook Marketplace it shared a seller's building address without permission, accepted CA$10 against a CA$15 ask, and told the buyer "Yep I'm here!" when he wasn't ([Yahoo Finance](https://finance.yahoo.com/technology/ai/articles/man-says-metas-ai-agent-134500315.html)).

The only cluster with verified cash losses today is Amazon Rufus. One seller documented Rufus asserting an item was wall-mountable, retracting ("the 2600 is designed for desk/table placement, not wall mounting"), then reverting; the buyer relied on it, filed an A-to-Z claim refusing return postage, and the seller "lost the dispute… used item received back, paid shipping and Amazon fees," after which Amazon closed the case and told the seller to open a new one ([Seller Forums](https://sellercentral.amazon.com/seller-forums/discussions/t/dec2650c-03db-4a66-a746-01acc49c2718)). A vehicle-parts seller wrote that "accurate vehicle compatibility information is the largest and most important barrier for successful sales" and asked for "the ability to simply disable rufus at the ASIN level"; Amazon confirmed no such opt-out exists ([Seller Forums](https://sellercentral.amazon.com/seller-forums/discussions/t/ad79306c-37ca-4b4e-a995-4dd047fbb4cf)). This is the template for what Muse and Dots will produce on the open web: an agent summarizes a product page, the shopper (or the agent) buys on that summary, and the merchant refunds. The HN reaction to the Amazon block made the same prediction: "The return rate for AI-purchased products is probably much higher than when a human reviews the page" ([Hacker News](https://news.ycombinator.com/item?id=49789982)), and "Amazon Sellers pay from 30% to 50% for customer returns from their own pockets... if agent-identified purchases generate higher returns, Amazon will crack down" ([Hacker News](https://news.ycombinator.com/item?id=49789982)).

The bot-versus-buyer problem is the one that silently destroys revenue. Fraud screening "was built to catch exactly the pattern an agent produces: a checkout completed in seconds, from a data-center IP address, on an account with no browsing history behind it—the same fingerprint a card-testing bot leaves" ([Startup Fortune](https://startupfortune.com/shopify-lets-ai-agents-finish-checkout-on-its-two-million-stores/)). Operator Trevor Fenner put it plainly: "I don't know how your fraud tool scores an order submitted by an agent inside the buyer's session," and recommended a $1,500 manual-review threshold for the first 30 days plus a separate dispute reserve ([eCommerce Paradise](https://ecommerceparadise.com/shopify-ai-agents-submit-orders/)). "False positives show up as nothing at all—the over-blocked agent doesn't file a support ticket or send an angry email, it just doesn't convert" ([SureBright](https://www.surebright.com/blog/cloudflares-blocking-ai-agents-on-your-store---is-that-good-news-or-harmful-for-sales)). The classifier gap is two-sided: Signifyd reports card-testing attacks up **175% YoY** and account takeover up 78% in early 2026 ([Signifyd](https://www.signifyd.com/news-releases/state-of-fraud-report/)), and Cloudflare's 15 Sept default change now blocks "Agent" bots on ad-carrying pages ([PYMNTS](https://www.pymnts.com/news/artificial-intelligence/2026/cloudflare-blocks-ai-agents-from-ad-supported-pages/)). An audit of 20 "agent-ready" Shopify stores found **35% never reached checkout and 25% had silent add-to-cart failures** ([GitHub MythrilS](https://github.com/MythrilS/agent-ready-checkout)), so merchants' own anti-bot layers are already breaking the agent sales they are enrolled in by default.

Measurement breakage is structural rather than a bug. For Muse direct checkout on Shopify, "Browser pixels won't fire… Google Analytics won't track direct checkout transactions; only server-to-server events fire… orders never load your storefront" ([Naughton & Bird](https://naughtonandbird.com/signals/shopify-meta-ai-channel-agentic-storefronts)). Agent-driven add-to-cart events pollute Advantage+ and Smart Bidding, and one worked example shows CVR falling from 2.5% to 1.8% from traffic-mix shift alone ([MNT Future](https://mntfuture.com/blog/ai-agent-traffic-ecommerce-bot-detection)). Shopify merchants describe AI-assisted sessions landing as "Direct or Organic" and stores being "silently excluded" from agent results because of weak structured data; one agency saw a client receive "about 20 confirmed orders referred by AI shopping assistants (mostly ChatGPT) over six weeks" ([Shopify Community](https://community.shopify.com/t/has-anyone-actually-seen-ai-referred-orders-chatgpt-shopping-in-their-shopify-analytics-yet/681884)). Only **11% of SMBs** are "agent-ready" and 15% have structured product data agents can use ([Forkast](https://forkast.news/only-11-of-small-merchants-are-ready-for-ai-shopping-agents/)). For restaurants the pain is scarcity hoarding, not payments: "We are dehumanizing the last standing experience that is still totally human," said Roni Mazumdar of Dhamaka and Semma, while Resy banned diners whose agents gamed reservations ([CNN](https://www.cnn.com/2026/09/23/tech/ai-agent-restaurant-reservations-instinct-resy-cec)). DoorDash's new text-to-order agent, which reads order history and charges a stored card, sends nearly half its orders to restaurants the customer has never used and delivers orders "without standard app metadata" ([Restaurant Business](https://www.restaurantbusinessonline.com/technology/text-order-doordash-moves-beyond-app)).

One caveat shapes everything: as of 3 Oct 2026 no merchant has publicly reported a specific Muse or Dots order being auto-cancelled by fraud tooling, charged back, or returned. The complaints above are either about adjacent agents (Rufus, ChatGPT referrals, Instinct) or anticipatory. The screener should be designed for the problem the Rufus and Shopify threads prove exists, with Muse/Dots as the accelerant.

## Returns abuse already costs $100B and wallet-backed agents make it effortless

The baseline is enormous and well measured. NRF and Happy Returns put 2025 US retail returns at **$849.9B, 15.8% of sales and 19.3% of online sales**, with 9% of returns fraudulent, and among retailers tracking it, increases in overstated-quantity returns (71%), empty-box returns (65%) and decoy/counterfeit returns (64%) ([NRF](https://nrf.com/media-center/press-releases/consumers-expected-to-return-nearly-850-billion-in-merchandise-in-2025)). LiquiDonate estimates 15% of returns are fraudulent, $25–30 processing cost per returned item, and $13.70 lost per $100 returned ([Yahoo Finance](https://finance.yahoo.com/news/liquidonate-shares-uncomfortable-reality-check-203235213.html)); Riskified says "nearly 1 in 4 refund dollars are linked to abusive behavior" ([PYMNTS](https://www.pymnts.com/news/retail/2026/ai-generated-damage-claims-trigger-retail-crackdown-on-return-fraud/)). The three numbers differ because "fraud" (empty box, counterfeit) and "abuse" (wardrobing, bracketing, policy exploitation) are different buckets, and a screener should score them separately. The most directly relevant Shopify-SMB benchmark comes from Loop's analysis of 23.4M returns: **11.4% of return value flagged high-risk, $120 average fraudulent return**, 65.2% of merchants charging fees on some returns, average refund window 39 days ([Loop Returns](https://www.loopreturns.com/reports/retention-benchmarks-2026/)).

Generative AI has already changed the consumer side. Riskified's June 2026 survey of 2,091 consumers found **50% use GenAI tools like ChatGPT or Claude to draft return claims**, 85% accept at least one deceptive return behaviour as normal, 42% bracket and 24% think wearing an item before returning is acceptable ([BusinessWire](https://www.businesswire.com/news/home/20260622536790/en/Return-Abuse-Goes-Mainstream-as-Nearly-Half-of-Consumers-Use-AI-in-Return-Claims-New-Riskified-Research-Finds)). AI-generated damage evidence is now daily: Boll & Branch's CEO spotted photos where cotton fraying "did not look like anything cotton does," fake UPS/USPS drop-off receipts, fabricated police reports and altered return labels, and Yofi's CEO described the trend going "from seeing it onesie-twosie to daily" ([Modern Retail](https://www.modernretail.co/technology/from-boll-branch-to-bogg-brands-are-battling-a-surge-of-ai-driven-return-fraud/)); one ring bought cheap goods, generated AI "broken" images, took instant refunds and kept everything for **$800,000** ([PYMNTS](https://www.pymnts.com/news/retail/2026/ai-generated-damage-claims-trigger-retail-crackdown-on-return-fraud/)). Organized refund-as-a-service operates on Telegram, with Amazon suing groups like REKK (operator arrested in Lithuania, €6M seized) and the DOJ's "Operation Chargeback" indicting Noir's Luxury Refunds and Artemis ([Amazon](https://trustworthyshopping.aboutamazon.com/inside-amazons-fight-against-refund-fraud)). The "double-dip" (refund on return plus a chargeback on the same order) recurs because auto-refund on carrier scan releases money days before warehouse inspection while the chargeback window is still open ([RefundSentry](https://refundsentry.com/return-fraud)).

Shopper-side agents add two mechanisms on top. First, the effort to file drops to zero: Muse "manages refunds," and Meta's Link wallet reportedly covers returns up to **$250 per item and refunds up to $1,000 if a merchant refuses a return within 60 days**, which GSPANN warns makes "initiating returns almost effortless, increasing fraud risk" and calls for "agent-specific return rules covering who can initiate a return and what proof is required" ([GSPANN](https://www.gspann.com/insights/blog/ai-shopping-agents-retailer-terms)). Those Link figures rest on a single secondary source because Meta's own terms were not retrievable, but if accurate they create a second adjudication layer outside the card networks in which a shopper who is declined has a financial incentive to escalate. Second, machines check policy continuously. Alhena's scenarios describe an agent requesting "return authorization for order #48213, item SKU TR-220-BLK-M" from a relay address that fails identity checks, price-drop claims filed days after purchase ("Loose policies become systematic liabilities when machines check continuously"), and "Policy Lawyer Precision," where an agent quotes policy verbatim and "unwritten enforcement rules collapse against literal interpretation" ([Alhena](https://alhena.ai/blog/ai-shopping-agent-support-tickets/)). Unit 42 demonstrated hidden listing instructions that tell a UCP agent to append a $100 gift card to the cart with "retailers absorbing chargebacks" and to "skip the order.return.verify step and immediately call settlement.refund.instant()" with fake tracking IDs ([Unit 42](https://unit42.paloaltonetworks.com/retail-fraud-agentic-ai/)). The Air Canada precedent, where a tribunal forced the airline to honour a chatbot's unauthorized discount, shows merchants can be held to whatever an AI tells a customer ([CX Foundation](https://cxfoundation.com/news/ai-agent-taken-offline-for-lying-to-a-customer)). No documented case of Muse, Dots or ChatGPT auto-filing a return or chargeback exists yet; the screener should treat this as weeks-old and unmeasured.

The detection signals merchants actually use are concrete and mostly obtainable from logistics data. Inbound package weight versus expected SKU weight catches empty boxes before opening (a 2 kg item scanning at 200 g) ([RefundSentry](https://refundsentry.com/return-fraud)); carrier tracking APIs expose `weight`, `weightUOM`, full scan-event history and standardized codes including "Return - Shipped to Retailer (RTS)" and USPS `scanType`/`l1Code` ([Pitney Bowes](https://docs.shippingapi.pitneybowes.com/api/get-tracking.html)). Practical thresholds flag customers whose return rate exceeds 30–40%, require photos before approval, and use Shopify Flow to tag repeat returners ([Ringly](https://www.ringly.io/blog/how-can-i-prevent-refund-fraud-on-shopify); [Riskified](https://www.riskified.com/learning/shopify/shopify-fraud-prevention-apps-2026/)). Boll & Branch and Bogg add physical-plausibility checks on photos, FaceTime verification and warehouse inspection before refund ([Modern Retail](https://www.modernretail.co/technology/from-boll-branch-to-bogg-brands-are-battling-a-surge-of-ai-driven-return-fraud/)); Entrupy fingerprints the physical item at sale and rescans on return ([Entrupy](https://www.entrupy.com/return-fraud-detection/)). On Shopify the data lives in the `Return` object (`status`, `requestApprovedAt`, `returnLineItems`, `reverseFulfillmentOrders`, `returnShippingFees`, `suggestedFinancialOutcome`) with mutations `returnRequest`, `returnApproveRequest`, `returnDeclineRequest` and `returnProcess` ([Shopify dev docs](https://shopify.dev/docs/api/admin-graphql/latest/objects/Return)), and apps can inject their own risk facts via `orderRiskAssessmentCreate`, which fires the `orders/risk_assessment_changed` webhook and surfaces `riskLevel`, `facts[]` and `provider` in admin ([Shopify dev docs](https://shopify.dev/docs/api/admin-graphql/latest/objects/OrderRiskAssessment)). The empty-box, FTID and double-dip patterns are fully detectable from logistics and payment data alone; wardrobing and AI-photo fraud require inspection or image forensics.

## "My agent did it" disputes collide with evidence rules built for browsers

The card-network rules a screener must encode changed in 2026 and all of them reward data captured before the sale. Visa Compelling Evidence 3.0 lets a merchant defeat a reason code 10.4 "Other Fraud — Card-Absent" dispute by showing **two prior undisputed transactions on the same credential, each 120–365 days old**, where at least two of {account ID, shipping address, IP address, device ID/fingerprint} match across all three transactions and at least one match is IP or device ([Chargebacks911](https://chargebacks911.com/prevent-chargebacks/prevent-visa-disputes/visa-compelling-evidence-3-0/)). Stripe's implementation exposes this as `enhanced_eligibility_types: ["visa_compelling_evidence_3"]`, `evidence.enhanced_evidence.visa_compelling_evidence_3.{disputed_transaction, prior_undisputed_transactions[]}` with sub-fields `customer_account_id`, `customer_device_fingerprint`, `customer_device_id`, `customer_email_address`, `customer_purchase_ip`, `shipping_address`, `merchandise_or_services`, `product_description`, plus `evidence_details.enhanced_eligibility.visa_compelling_evidence_3.status` (`requires_action|qualified|not_qualified`); Stripe autofills from prior charges and provides test card `4000000404000038` ([Stripe](https://docs.stripe.com/disputes/api/visa-ce3)). From **24 Oct 2026**, transactions at other merchants may count as qualifying evidence, partly closing the first-time-buyer hole ([Chargeflow](https://www.chargeflow.io/blog/visa-compelling-evidence-3-0-explained)).

The Visa Acquirer Monitoring Program punishes disputes received, not lost. Its ratio is (TC40 fraud reports + TC15 non-fraud disputes) ÷ TC05 settled card-not-present transactions, the merchant threshold dropped from 2.2% to **1.5% on 1 Apr 2026**, fees run about $8 per item, and a US merchant is "excessive" at ≥1.5% and ≥1,500 items in a month ([Merchant Risk Council](https://merchantriskcouncil.org/learning/resource-center/member-news/blog/2026/stricter-vamp-ratio-thresholds-are-now-in-effect-heres-how-to-stay-compliant)). Stripe is explicit: "the card networks don't consider how many disputes you win or lose, only how many you receive — a withdrawn dispute still counts" ([Stripe](https://docs.stripe.com/disputes/best-practices)). What removes items from the ratio is Rapid Dispute Resolution (auto-refund by rule), a CE 3.0 pre-dispute match via Verifi Order Insight, or refunding on a CDRN/Ethoca alert before the chargeback is filed ([Merchant Risk Council](https://merchantriskcouncil.org/learning/resource-center/member-news/blog/2026/stricter-vamp-ratio-thresholds-are-now-in-effect-heres-how-to-stay-compliant)). Mastercard's reason codes 4837 (No Cardholder Authorization) and 4853 (Cardholder Dispute) give the cardholder 120 days to file and the merchant 45 days to respond ([Chargeflow](https://www.chargeflow.io/blog/mastercard-chargeback-survival-guide)); its global chargebacks rose **41% from 238M (2023) to 337M (2026)** ([Chargebacks911](https://chargebacks911.com/chargeback-stats/)). The economics argue for prevention over representment: merchants win 44.6% of chargebacks they fight but net-recover only **10.7%**, 83.4% report rising friendly fraud, and 69% rely solely on in-house staff ([Chargebacks911](https://chargebacks911.com/chargeback-stats/)). Stripe's own win-likelihood scale tops out at 60% and it warns "it's very difficult to overturn a disputed payment" ([Stripe](https://docs.stripe.com/disputes/best-practices)). A Shopify merchant whose rate crossed 1% after three fraudulent chargebacks lost Shop app eligibility, which requires a rate below 1% over six months ([Shopify Community](https://community.shopify.com/t/chargeback/350299)).

Agent orders break this evidence model at its root. For an agent-placed order, "device fingerprints [are] unavailable (API, not browser), no browsing history or session behavior, IP belongs to the AI platform's servers not the customer — exactly the elements CE 3.0 relies on" ([Chargeflow](https://www.chargeflow.io/blog/ai-agent-chargeback-liability)). A Muse order arrives from a Cloudflare/Fastly-egress Linux VM with a uniform fingerprint shared across all Muse users, and each order may carry a fresh Link single-use card, so there is no "same credential" history to match. The dispute itself is a new, durable species of friendly fraud: the consumer can say "didn't authorize that, my agent did" "without technically lying," and one risk-intelligence unit reports disputes on agent-initiated transactions running **~2.4x comparable human CNP** (a single-vendor figure not independently corroborated) ([Fraudbeat](https://www.fraudbeat.com/agentic-commerce-disputes-friendly-fraud/)). Chargeflow's evidence playbook names the patterns ("Forgotten Agent Purchases," "Misinterpreted Intent," "Fraud Hiding Inside Automation," "Trust-Break Chargebacks") and the new evidence merchants must capture: proof of delegated authority, customer-set parameters such as spend caps and categories, scope-compliance evidence, and notification timestamps that enabled cancellation; "Authorization does not mean the customer wanted that specific product, at that specific price, from that specific merchant" ([Chargeflow](https://www.chargeflow.io/blog/agentic-commerce-chargebacks-the-evidence-playbook-merchants-need)). An issuer-side view agrees that "fighting disputes is turning into stopping them from being filed" and that the qualifying data must be captured "before sale, not after chargebacks occur," which disadvantages small merchants against data-rich platforms ([The Paypers](https://thepaypers.com/fraud-and-fincrime/expert-views/chargebacks-issuer-fraud-verdicts-and-the-impact-of-agentic-commerce)). Shopify's buyer-authorization click is "a thinner paper trail than what card networks currently expect," and IDC's Heather Hershey confirms that "if Muse purchases a product that a user didn't actually want, the cost of returns or disputes lands on the merchant" ([Startup Fortune](https://startupfortune.com/shopify-lets-ai-agents-finish-checkout-on-its-two-million-stores/); [Shopifreaks](https://www.shopifreaks.com/shopify-and-paypal-partner-with-muse-for-almost-agentic-commerce/)).

The networks have shipped identity and mandate rails but not dispute rules. Visa TAP produces "a cryptographically verifiable record of who approved what, when, and through which agent," yet "agent identity and mandate data won't appear in clearing data or dispute evidence overnight" and no agent-specific reason codes exist ([Rivero](https://rivero.tech/blog/agentic-commerce-disputes-liability)). Visa's model includes an agent-as-merchant-of-record option where the agent platform "owns first-line disputes" ([eco.com](https://eco.com/support/en/articles/15192003-mastercard-agent-pay-vs-visa-trusted-agent-2026-compared)), and a secondary source describes Mastercard "Verifiable Intent" with two new dispute grounds (unauthorized agent action within a mandate; repudiation of the mandate) routed to the agent operator ([Digital Applied](https://www.digitalapplied.com/blog/mastercard-verifiable-intent-trust-agentic-commerce)), but the Mastercard primary page was unreachable and Chargeflow states that "neither [Visa nor Mastercard] has published a binding chargeback rule for agent disputes" ([Chargeflow](https://www.chargeflow.io/blog/ai-agent-chargeback-liability)). Stripe's Shared Payment Token "protects the consumer's credentials but does little to protect the merchant from intent disputes" ([FinTech Wrap Up](https://www.fintechwrapup.com/p/deep-dive-the-hidden-liability-of)). Reg E "does not clearly resolve whether agent authorization counts as consumer consent," no US federal framework exists, and VAMP and Mastercard's ECM "do not distinguish between human-initiated and AI-initiated disputes" ([Chargeflow](https://www.chargeflow.io/blog/agentic-commerce-regulation-what-merchants-need-to-know)). Merchants know this: **93% believe AI providers should bear financial liability**, while only 3% of transactions currently involve agents ([Forkast](https://forkast.news/only-11-of-small-merchants-are-ready-for-ai-shopping-agents/)).

The practical toolchain for a screener is therefore Stripe's `Dispute` object and Shopify's `ShopifyPaymentsDispute`. Stripe's `reason` enum includes `fraudulent`, `product_not_received`, `product_unacceptable`, `credit_not_processed`, `duplicate`, `unrecognized` and `customer_initiated`; `status` runs `warning_needs_response` through `needs_response`, `under_review`, `won`, `lost` and `prevented`; `evidence_details` carries `due_by`, `has_evidence`, `past_due`, `submission_count`; and `payment_method_details.card.network_reason_code` exposes the raw network code ([Stripe](https://docs.stripe.com/api/disputes/object)). The `evidence` hash fields a screener should pre-populate include `customer_purchase_ip`, `customer_email_address`, `shipping_address`, `shipping_tracking_number`, `shipping_documentation`, `access_activity_log`, `customer_communication`, `refund_policy_disclosure`, `refund_refusal_explanation`, `duplicate_charge_id` and `uncategorized_text`; updating any field submits the whole hash unless `submit=false` ([Stripe](https://docs.stripe.com/api/disputes/object)). Packages must be PDF/JPEG/PNG, ≤4.5 MB, under 50 pages (19 for Mastercard), one file per evidence type; Stripe auto-includes AVS, CVC and IP results, full delivery address beats city/ZIP alone, and a cardholder's withdrawal or prior refund is "discrediting evidence" ([Stripe](https://docs.stripe.com/disputes/best-practices)). Shopify's `ShopifyPaymentsDispute` exposes `amount`, `disputeEvidence`, `evidenceDueBy`, `evidenceSentOn`, `finalizedOn`, `initiatedAt`, `order`, `reasonDetails`, `status` and `type` (inquiry vs chargeback), queryable by status and initiation time ([Shopify dev docs](https://shopify.dev/docs/api/admin-graphql/latest/objects/ShopifyPaymentsDispute)).

## Agent identity exists on paper, but Muse and Dots don't use it

The de-facto production mechanism is IETF Web Bot Auth, adopted as `draft-ietf-webbotauth-httpsig-protocol-00` on 1 Sept 2026 and authored by Cloudflare and Google engineers ([IETF](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/)). It layers on RFC 9421 HTTP Message Signatures: requests carry `Signature`, `Signature-Input` and `Signature-Agent` headers; required signature components are `@authority` (or `@target-uri`), `created`, `expires`, `keyid` (a base64url JWK SHA-256 thumbprint per RFC 7638) and `tag="web-bot-auth"`, with an optional 64-byte `nonce`; keys are published as a JWKS at `/.well-known/http-message-signatures-directory` using EdDSA on Ed25519 or RSASSA-PSS/SHA-512; and nonce replay enforcement is explicitly "the origin's responsibility" ([IETF architecture draft](https://datatracker.ietf.org/doc/html/draft-meunier-web-bot-auth-architecture)). Cloudflare's verifier performs seven checks (headers present, fetch key, validate `created`/`expires`, nonce uniqueness, tag validity, reconstruct signature base, Ed25519 verify), and its example header reads `Signature-Input: sig2=("@authority" "@path"); created=1735689600; expires=1735693200; keyid="..."; alg="Ed25519"; nonce="..."; tag="web-bot-auth"` ([Cloudflare](https://blog.cloudflare.com/secure-agentic-commerce/)). Since **1 July 2026**, signed agents receive Cloudflare's "Verified" classification with a "Direct versus Intermediary access" metadata field, where Intermediary covers agentic services operated by many end users; behaviour categories include Search, Agent, Training and Transact ([Cloudflare](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)). DataDome and Akamai (via its "Know Your Agent" framework with Skyfire, Experian and Visa) support the same scheme ([Akamai](https://www.akamai.com/newsroom/press-release/akamai-unveils-agentic-security-framework-to-power-trusted-ai-driven-interactions-and-commerce)).

The payment-network layer reuses the same primitive with different tags and adds consumer binding. Visa's Trusted Agent Protocol uses `tag="agent-browser-auth"` for product pages and inventory checks and `tag="agent-payer-auth"` for checkout; its Agentic Consumer Recognition object carries `nonce`, `idToken`, `contextualData` (`countryCode`, `zip`, `ipAddress`, `deviceData`), `kid`, `alg` and `signature`; the Agentic Payment Container carries `paymentCredentialsHash` and card metadata including `paymentAccountReference`; the `idToken` is a JWT with OIDC claims including `sub`, `amr`, `auth_time`, `email_verified` and masked `phone_number_mask`/`email_mask`; Visa publishes keys at `https://mcp.visa.com/.well-known/jwks`; and merchants must enforce an **8-minute** `created`/`expires` window and nonce replay checks ([Visa TAP spec](https://developer.visa.com/capabilities/trusted-agent-protocol/trusted-agent-protocol-specifications)). This is the only rail that hands the merchant a signed statement of how and when the human authenticated. Mastercard Agent Pay instead pushes proof into the token: Agentic Tokens "bind a tokenized card credential to a specific agent, a specific merchant scope, and a specific consent policy," the authorization message carries an agent-flag indicator, and mandates (spend ceilings, MCCs, time windows) are validated by the issuer in real time ([eco.com](https://eco.com/support/en/articles/15192001-what-is-mastercard-agent-pay-ai-agent-commerce-protocol-in-2026)); on 30 Sept 2026 Mastercard added "a probability score indicating likelihood a transaction was initiated by an AI agent" for issuers and merchants, with no field names published ([PYMNTS](https://www.pymnts.com/mastercard/2026/mastercard-deploys-new-risk-insights-to-support-agentic-payments/)). Stripe's Shared Payment Tokens are the only self-serve option: a seller charges with `POST /v1/payment_intents` and `payment_method_data[shared_payment_granted_token]=spt_123` under `Stripe-Version: 2026-09-30.preview`, the `shared_payment.granted_token` object exposes `usage_limits.max_amount`, `usage_limits.expires_at`, `deactivated_reason` and card `brand`/`last4`, the webhook `shared_payment.granted_token.deactivated` fires on consume/expire/revoke, and a `POST /v1/test_helpers/shared_payment/granted_tokens` helper plus `npx @stripe/link-cli spend-request create` exist for testing ([Stripe](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens.md?agent-seller=seller)). An SPT proves a bounded allowance, not human presence. Google's AP2 supplies the missing intent layer as user-signed Intent, Cart and Payment Mandates expressed as W3C Verifiable Credentials ("a secure, unchangeable record of exact items and price" signed before purchase) ([Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/announcing-agents-to-payments-ap2-protocol)), and UCP carries those mandates: a merchant publishes `/.well-known/ucp` with `ucp.version` (`"2026-08-25"`), `ucp.capabilities` such as `dev.ucp.shopping.checkout`, `dev.ucp.shopping.order` and `dev.ucp.shopping.policy.return`, `ucp.payment_handlers` and a `keys[]` JWK Set, while agents announce themselves with `UCP-Agent: profile="https://agent.example/profiles/shopping-agent.json"` and customers link accounts through OAuth 2.0 identity linking (`dev.ucp.common.identity_linking`) ([ucp.dev](https://ucp.dev/specification/overview)). OpenAI's ACP checkout spec requires `Authorization`, `API-Version`, `Idempotency-Key`, `Request-Id`, `Signature`, `Timestamp` and `User-Agent` headers and HMAC-signed `order_created`/`order_updated` webhooks with statuses including `manual_review`, but "does not specify risk/fraud signal fields" ([OpenAI](https://developers.openai.com/commerce/specs/checkout)).

| Mechanism | What it proves to the merchant | Status (Oct 2026) | Used by Muse/Dots? |
|---|---|---|---|
| Web Bot Auth (`tag="web-bot-auth"`) | Agent operator holds a published key | IETF WG draft; live at Cloudflare, DataDome | No ([GSPANN](https://www.gspann.com/insights/blog/ai-shopping-agents-retailer-terms)) |
| Visa TAP (`agent-payer-auth`, `idToken`) | Agent identity plus how/when the human authenticated | Spec public; EU/India pilots | No evidence |
| Mastercard Agentic Token + agent flag | Issuer-validated mandate scope; AI-probability score | US cardholders since Nov 2025 | No evidence |
| Stripe SPT | Bounded allowance (merchant, amount, expiry) | Preview; self-serve sandbox | Muse uses Link single-use cards, not documented as SPT |
| AP2 mandates via UCP | User-signed cart/intent record | Spec v0.2; Shopify UCP-enabled by default | Not documented |
| UA token + IP list (`ChatGPT-User`, `Google-Agent`, `Claude-User`) | Declared crawler/fetcher identity | Production | No dots/Muse token exists |
| Amazon `Agent/[name]` UA convention | Contractual self-declaration | Amazon terms | No |

Two weaknesses bound what any of this can do. First, "key generation is free, so being a well-behaved unknown bot is the same as being an unidentified bot… It is only useful for whitelisting bots, not for banning bad ones" ([Hacker News](https://news.ycombinator.com/item?id=45055452)); as Prosopo puts it, "A signature tells you who. It does not tell you what for" ([Prosopo](https://prosopo.io/blog/web-bot-auth-signed-agents/)). Second, agentic browsers blend control modes: Comet "might start with human interaction and shift into automated mode mid-flow, using the same browser and fingerprint," and tools like Skyvern route through residential AT&T-associated IPs and strip automation markers ([Castle](https://blog.castle.io/from-detection-to-trust-the-evolving-challenge-of-ai-bot-authentication/)). DataDome's conclusion for Muse is that merchants should detect by intent and behaviour (single-user checkout versus coordinated multi-agent scraping) rather than identity, noting that 7 in 10 sites let spoofed agents through when they claimed trusted identities ([DataDome](https://datadome.co/threat-research/meta-muse-doesnt-declare-itself-heres-why-that-matters/)). The honest model for a merchant in Oct 2026 is three populations: signed agents (policy by identity plus rate limits), declared-but-unsigned agents (UA token plus IP list), and undeclared agents in real browsers, which is where Muse and Dots live and where only behavioural signals, step-up at checkout and network-level probability scores apply.

## A screener should join four event streams and score three agent populations

Everything above converges on a gap no vendor fills for SMBs: enterprise fraud platforms (Signifyd, Riskified, Forter) score at checkout on quote-priced percent-of-GMV contracts, returns platforms (Loop, Narvar) score at the return request, and chargeback tools (Chargeflow at 25% of recovered amounts, $29 per deflected alert) act after the dispute; nothing correlates the three streams for one order or watches for the double-dip and scan-versus-refund timing ([Redo](https://redo.com/resources/articles/comparisons/fraud-platform-pricing); [Redo](https://redo.com/resources/articles/comparisons/chargeback-alternatives-shopify)). A Shopify-plus-Stripe merchant can obtain every input from four sources: Shopify Admin GraphQL (`Order`, `Return`, `ReverseFulfillmentOrder`, `OrderRiskAssessment`, `ShopifyPaymentsDispute`), the Stripe Disputes API with CE 3.0 autofill, carrier tracking APIs (scan events, weight), and support email with photo attachments; the one blind spot is checkout-time IP/device capture, which must be instrumented before the order because Stripe only has what "your integration collects and passes… when your customer makes a payment" ([Stripe](https://docs.stripe.com/disputes/best-practices)).

The screener's first module is a per-order **evidence vault** written at checkout, because every rule in the previous two sections rewards pre-sale capture. For human-browser orders it stores `customer_purchase_ip`, a device fingerprint or ID, account ID, email and shipping address in exactly the shapes Stripe's `visa_compelling_evidence_3` sub-fields expect, so the Oct 2026 CE 3.0 autofill and the 24 Oct multi-merchant evidence change work without reconstruction. For agent orders it stores the replacement evidence: the `Signature-Agent` directory and `keyid`, the TAP `idToken` claims (`sub`, `amr`, `auth_time`), the SPT `usage_limits` and `deactivated_reason`, any AP2 mandate hash and UCP agent profile URL, the Mastercard agent flag, the Shopify channel/referrer attribution, and the timestamp and content of the confirmation email, which for ghost orders is "our only window" to the customer ([Shopify Community](https://community.shopify.com/t/agentic-storefronts-your-post-purchase-tools-dont-fire-on-in-chat-checkout-orders-is-anyone-thinking-about-this/592304)). Chargeflow's advice to "log agent-initiated transactions separately" becomes a first-class `agent_population` field with values `signed`, `declared`, `undeclared-suspected` and `human` ([Chargeflow](https://www.chargeflow.io/blog/ai-agent-chargeback-liability)). The `undeclared-suspected` classifier is the technically interesting part: it should combine the Muse fingerprint cluster (identical Linux Chrome hardware/rendering signature across sessions, Cloudflare/Fastly egress ASN, no scroll or hover events, straight-line navigation to checkout, seconds-long sessions) that DataDome and Neos Chronos describe ([DataDome](https://datadome.co/threat-research/meta-muse-doesnt-declare-itself-heres-why-that-matters/); [Neos Chronos](https://neoschronos.com/insights/when-ai-agents-become-the-customer-meta-muse-ecommerce/)) with payment-side tells such as a fresh single-use Link card per order and a name mismatch between order and account ([Alhena](https://alhena.ai/blog/ai-shopping-agent-support-tickets/)). A hackathon verifier for the signed population is small: parse `Signature-Input`, require `tag` in {`web-bot-auth`, `agent-browser-auth`, `agent-payer-auth`}, resolve `keyid` against the `Signature-Agent` directory, Visa's `https://mcp.visa.com/.well-known/jwks` or a UCP profile's `keys[]`, enforce `created`/`expires` and a local nonce store, and verify Ed25519 with Cloudflare's Apache-2.0 `http-message-sig` and `web-bot-auth` npm packages or the Caddy plugin ([GitHub cloudflare/web-bot-auth](https://github.com/cloudflare/web-bot-auth)).

The second module scores return requests against a signal taxonomy drawn from what merchants actually catch.

| Signal family | Concrete features | Source | Catches |
|---|---|---|---|
| Customer history | return rate >30–40%, refund-$/order-$ ratio, prior INR/damaged claims, account age, first-order flag | Shopify `Order`/`Return` | Serial abuse, refund-as-a-service |
| Order shape | bracketing (multiple sizes/colours of one SKU), high-resale SKU, ship-to ≠ billing, gift-name mismatch | Shopify `Order` | Wardrobing, bracketing, reshipping |
| Identity linkage | shared device/IP/address/payment across accounts; relay email domains; agent population | Evidence vault | Multi-account rings, agent relay addresses |
| Logistics | carrier scan present/absent, scan-to-refund gap, inbound weight vs SKU weight, label/tracking mismatch, delivery address vs return origin | Carrier tracking API (`weight`, `scanType`, RTS codes) | Empty box, FTID, premature auto-refund |
| Claim artifacts | EXIF/metadata, duplicated image regions, generator watermarks, receipt authenticity, physical-plausibility of damage | Return portal/email attachments | AI-generated damage photos, fake drop-off receipts |
| Velocity | claims per address/device per 30 days; policy-quote density in claim text; price-drop claims after purchase | Support inbox | Agent-driven "policy lawyer" and price-match sweeps |
| Double-dip | open return/refund plus a `Dispute` on the same `charge` | Stripe `Dispute` + Shopify `Return` | Refund-then-chargeback |

Each return request should produce a tiered recommendation rather than a binary: instant refund, exchange-first, refund on warehouse inspection, require photo or video verification, or decline with a policy citation. Riskified's "Dynamic Returns" and Signifyd's low/moderate/high scoring already validate tiered treatment commercially ([BusinessWire](https://www.businesswire.com/news/home/20260112619982/en/Riskified-Analysis-Reveals-1-in-4-Refund-Dollars-Is-Abusive-Introduces-Dynamic-Returns-a-New-Policy-Protect-Feature-to-Safeguard-Revenue-While-Increasing-Customer-Satisfaction); [Signifyd](https://www.signifyd.com/news-releases/signifyd-return-abuse-prevention/)), and 56% of consumers say they prefer tiered policies ([BusinessWire](https://www.businesswire.com/news/home/20260622536790/en/Return-Abuse-Goes-Mainstream-as-Nearly-Half-of-Consumers-Use-AI-in-Return-Claims-New-Riskified-Research-Finds)). The recommendation can be pushed into Shopify admin through `orderRiskAssessmentCreate` so staff see `facts[]` next to the order, and through Shopify Flow tags for routing. For agent-originated claims the module should apply the "agent-specific return rules" GSPANN calls for: require the claim to come from the linked customer identity (UCP OAuth link or the original order email), require proof artifacts proportional to the agent population, and refuse automated instant-refund paths that Unit 42's `settlement.refund.instant()` scenario abuses ([GSPANN](https://www.gspann.com/insights/blog/ai-shopping-agents-retailer-terms); [Unit 42](https://unit42.paloaltonetworks.com/retail-fraud-agentic-ai/)).

The third module is a **dispute router** whose objective is minimizing VAMP/ECM items, not maximizing wins. On an Ethoca/CDRN alert or a Stripe `warning_needs_response` inquiry, it decides between refund-and-close (removing the item from the VAMP ratio), RDR-style auto-settlement, and representment; it should default to refund for likely friendly fraud on low-ticket orders and to representment only when the evidence vault contains a CE 3.0-qualified match or, for agent orders, a mandate record plus delivery proof. When it represents, it assembles the Stripe `evidence` hash automatically (one merged PDF per evidence type, ≤4.5 MB, 19 pages for Mastercard, full delivery address, policy screenshot as presented at checkout) and stages it with `submit=false` for human review, with the `due_by` deadline surfaced as a countdown ([Stripe](https://docs.stripe.com/disputes/best-practices)). A fourth, smaller module watches for the Rufus pattern on the merchant's own catalog: it diffs what agents could plausibly infer from the product page (fitment, compatibility, size, material) against structured attributes, flags ambiguities like "navy" versus "Midnight" that cause wrong-variant orders ([Alhena](https://alhena.ai/blog/ai-shopping-agent-support-tickets/)), and recommends moving facts into Shopify options or category metafields where agents read them ([Naughton & Bird](https://naughtonandbird.com/signals/shopify-meta-ai-channel-agentic-storefronts)). GSPANN's readiness advice is the same: "write for the constraint the shopper hands the agent, and store every fact where a machine can find it" ([GSPANN](https://www.gspann.com/insights/blog/ai-shopping-agents-retailer-terms)).

The tooling gaps to lean on are specific. Neither Shopify nor Stripe documents an "agent-originated" flag on `Order` or `Charge`, so the screener's population classifier is net-new. No Python Web Bot Auth library exists in Cloudflare's repo (TypeScript and Rust only). No vendor offers chargeback liability shift for agent orders, and no evidence format for mandates is accepted in representment, so a screener that stores mandates in a Stripe-evidence-ready shape is ahead of the networks. No per-SKU ground-truth feed to agents exists on Amazon or the open web. And no SMB product joins return, carrier and dispute streams. For a demo, Stripe SPT has a self-serve sandbox, Visa's `trusted-agent-protocol` repo ships a Python agent-registry, tap-agent and merchant-backend plus a Node CDN proxy ([GitHub visa](https://github.com/visa/trusted-agent-protocol)), AP2 has a Python SDK with sample merchant endpoints ([GitHub AP2](https://github.com/google-agentic-commerce/AP2)), and a Shopify dev store exposes the Return, Dispute and risk-assessment APIs. A convincing demo flow runs a signed TAP test agent and an unsigned "Muse-like" Chromium through the same store, shows the vault capturing different evidence for each, replays a double-dip return-plus-dispute, and produces a staged Stripe evidence package with a VAMP-impact estimate.

## Conclusion

The agent era inverts the merchant's traditional fraud posture. For twenty years the question at checkout was "is this a real cardholder?" and the evidence that answered it (IP, device, session depth) is precisely what Muse and Dots erase, while the question that now decides disputes ("did the human authorize this item, at this price, from this merchant?") has no network-accepted evidence format yet. Merchants were also auto-enrolled into this by Shopify, so the population most exposed to agent-driven returns and "my agent did it" disputes is the sub-$1M store with no fraud platform, which is the exact customer the enterprise vendors do not serve.

That makes the screener's real product the evidence vault rather than the scoring model: capturing CE 3.0 elements for humans and mandate/identity records for agents at order time, then spending that evidence in the pre-dispute window where VAMP and Mastercard's ECM actually count. The open question a hackathon cannot settle is whether the networks will carry agent identity into clearing and dispute data; if Visa TAP's `idToken` or AP2 mandates ever appear in representment, the merchants who already stored them per order win immediately, and if they do not, the same vault still turns the only lever merchants control today, refunding before the chargeback is filed, from a guess into a scored decision.
